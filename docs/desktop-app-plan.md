# 声骸评分与调谐建议：Windows 桌面程序技术方案

## 1. 项目目标

开发面向 Windows 的本地桌面程序，发布为 EXE，使用者无需安装 Python。

核心功能：

1. 选择角色或评分预设，并允许调整权重与目标分数。
2. 根据当前已激活的副词条，实时计算声骸评分。
3. 根据当前状态和目标分数，估计后续调谐的成功概率及材料成本。
4. 给出“继续激活下一条 / 停止并更换声骸”的实时建议及理由。
5. 部分权重由系统计算，其余由预设或用户设置提供。
6. 预留 OCR 识别当前词条的扩展能力；第一版允许手动录入。

沿用 [总体定义与术语](General-Definition.md) 和 [属性概率配置](../config/echo-stats.json)。主词条已筛选确定，不估计其获取概率及刷取成本。

## 2. 技术选型

**推荐：Python + PySide6 + PyInstaller。**

| 层次         | 选择                                  | 用途                                   |
| ------------ | ------------------------------------- | -------------------------------------- |
| 核心语言     | Python 3.12，后续升级经依赖验证后进行 | 权重、评分、概率与成本策略计算         |
| 桌面界面     | PySide6                               | 原生桌面窗口、表单、结果展示和信号更新 |
| 数值计算     | 标准库起步，按需使用 NumPy            | 离散概率计算及批量模拟                 |
| 配置存储     | JSON                                  | 属性概率、角色参数、权重预设、成本配置 |
| 测试         | pytest                                | 数据校验、算法边界及策略回归测试       |
| Windows 打包 | PyInstaller                           | 生成无需 Python 环境的 EXE 发布包      |
| OCR          | 独立可替换适配器，具体引擎后续选定    | 从截图提取词条类型与数值               |

选择 Python 的主要原因是便于验证概率模型和策略算法。实时加权评分计算量很小，不需要先采用 Rust 或 C++。完整策略搜索可能出现状态膨胀，需采用缓存、剪枝及后台计算；出现经过测量确认的性能瓶颈后再考虑加速。

### Windows 发布约束

- 第一阶段以 Windows x64 为发布目标。
- 可在 macOS 开发，但 Windows EXE 应在 Windows 环境或 Windows CI 中构建和测试；不把 macOS 打包视为 Windows 交叉编译方案。
- “EXE 桌面程序”不等于必须“单文件 EXE”。优先目录式发布包，验证稳定后再评估单文件或安装包。
- OCR 模型可能增加包体积和启动耗时，宜设计为可选组件，而不是首版强制依赖。
- 用户权重方案采用便携式存储：源码保存在项目根目录，打包后保存在 EXE 同目录，不覆盖内置默认配置。程序目录必须可写，写入失败时提示用户，不回退到用户应用数据目录；旧版用户目录方案仅在本地库不存在时只读迁移。
- 发布前检查依赖与 OCR 模型许可证；PySide6/Qt 的分发需满足适用许可要求。

### macOS 发布实现

- 使用同一份 [WWEcho.spec](../WWEcho.spec)，在 macOS 通过 [build-macos.sh](../build-macos.sh) 构建独立 `.app`，不改变 Windows 单文件 EXE 的构建方式；目标架构随构建环境。
- 权重采用便携式存储，保存到 `.app` 同级的 `weight-presets.json`，不写入应用包或用户应用数据目录。程序所在目录需可写；移动时同时携带 JSON，升级仅替换 `.app`。
- 构建时把当前项目方案库作为只读模板打包；外部库不存在时复制全部方案和最近选择，已有库绝不覆盖。macOS 打包版不自动读取旧版用户目录；源码及 Windows 迁移规则不变。
- 当前仅提供本地 ad-hoc 签名，未做 Developer ID 签名/公证。对外发布需另行处理 Gatekeeper 与 App Translocation；详细使用限制见 [README](../README.md#macos-应用打包与使用)。

## 3. 功能与界面

建议主窗口分为三个区域：

| 区域   | 内容                                                   |
| ------ | ------------------------------------------------------ |
| 参数区 | 角色、预设、权重模式、目标分数、成本折算与预算         |
| 声骸区 | Cost、主词条、等级、已激活副词条；预留“截图识别”入口   |
| 结果区 | 当前评分、可达分数上界、达标概率、预期成本及下一步建议 |

每次修改词条、权重或目标后自动更新结果。评分即时完成；较重的策略估算交给后台任务。输入变化时，旧任务结果不得覆盖新状态的结果。

区分以下结果，避免混淆：

- **当前评分**：仅对已知属性计分，第一版默认针对副词条。
- **最终潜力**：考虑剩余槽位后的分数上界及概率分布。
- **本件成功概率**：当前声骸按指定继续策略达到目标的概率。
- **重复尝试成本**：允许弃置、更换声骸后，获得一件达标声骸的期望净成本。

## 4. 权重机制

采用三种模式：**手动、预设、系统辅助计算**。

### 4.1 统一评分口径

固定值与百分点不能未经换算直接相加。建议先将词条数值换算为“参考满档比例”，再乘以权重：

$$
S = \sum_{i\in A} w_i\frac{x_i}{r_i}
$$

其中，$A$ 为已激活副词条集合，$x_i$ 为当前数值，$r_i$ 为该类型的参考数值（第一版取官方最高档），$w_i$ 为参考满档词条的分值。

该评分衡量当前预设下的属性价值，不自动等同于实际伤害提升百分比。若展示百分制，需固定并注明归一化基准；不能按已激活槽位数变化分母，否则实时评分不可直接比较。

### 4.2 系统计算的权重

系统辅助权重应来自**角色收益模型**，而不是词条出现概率或稀有程度。

输入可包括：角色基础属性、武器与套装、当前面板、技能倍率与伤害构成，以及共鸣效率需求。每个角色模型声明必需输入；缺少输入时回退到预设，并明确标注。

对于模型支持的属性，可计算增加一个参考词条前后的相对收益：

$$
g_i = \frac{F(\mathbf{a}+r_i\mathbf{e}_i)-F(\mathbf{a})}{F(\mathbf{a})}
$$

其中 $F$ 是明确声明的输出收益模型，$\mathbf{a}$ 是基准面板，$\mathbf{e}_i$ 表示对应属性方向。仅在基准输出有效且大于零时使用该公式，再按固定规则将 $g_i$ 转换为评分权重。

- 输出型角色可按指定技能循环的伤害收益估算权重。
- 治疗、生存与共鸣效率需求不能直接套用纯伤害权重；首版可使用预设或用户配置。
- 暴击上限、共鸣效率达标线等阈值会产生非线性收益。线性权重只是近似；完整模型可在后续支持直接计算收益。
- 比较调谐候选结果时必须固定同一基准面板；更换基准会重新计算并使旧缓存失效。

### 4.3 用户覆盖与可解释性

每个词条分别显示：系统建议权重、实际生效权重、来源，以及是否被用户覆盖。

优先级：**用户覆盖 > 有效的系统计算 > 角色预设 > 通用默认值**。用户可以取消单项覆盖，恢复自动权重。

配置应记录收益模型版本、参考值及输入参数，确保评分可复现。权重更新后，成本与继续建议同步重算。

## 5. 概率、成本与继续建议

### 5.1 概率模型

- 副词条类型按剩余候选池等概率抽取，同一声骸不重复。
- 档位使用官方非均匀概率，计算时对公示圆整值归一化。
- 主词条、小词条不参与副词条排重。
- 小规模结果优先枚举或动态规划；大规模结果可使用模拟，并显示样本量、误差或置信区间。
- 数值离散化、剪枝等近似必须注明，不能把模拟或近似结果称为精确概率。

### 5.2 成本输入

逐阶段升级经验、开孔素材消耗及弃置回收规则已按用户提供并确认的数据维护在 [激活成本配置](../config/activation-costs.json)：累计需求经验 4400/16500/39600/79100/142600，解锁等级 5/10/15/20/25，各开孔消耗 10 素材。经验按 500 最小单位累计补足并保留余量；强化和开孔不会失败，只有玩家主动弃置回收时才按累计实际投入返还 70% 经验和 30% 开孔素材，两类比例独立，经验向下取整到 500。成本模型假设未达标且停止投入时主动回收；达标后必须保留并继续升至 +25、开满五条，剩余经验与打孔器全部计入成功成本；若未达标保留不回收，则不适用回收抵扣。默认成本权重按材料本经验掉落 23000 与开孔素材 20 的供给比例估算后，将每 1000 经验权重取整为 0.8、每个素材权重为 1，胚子权重保留自定义的 1；成本按净经验点数 ÷ 1000 × 0.8 计算，原始经验数量不变。游戏货币和胚子刷取成本尚未提供，不得臆造为官方消耗。现已实现下述目标在当前 1000 格模型内的累计成本优化，不再使用新胚子概率门槛。

默认分别展示各种材料的期望净消耗。需要单一成本指标时，由用户设置折算权重；不同折算规则可能得到不同建议。

主词条刷取成本不纳入当前范围。换胚子可以默认视为已有合适主词条库存，但必须标注这一前提；用户设置的胚子机会成本需单独列出。

### 5.3 第一版决策目标

**在未达标时可以放弃并换胚子的情况下，尽量降低获得一件 +25、五条全开且达到目标分数声骸的期望净成本。**

将当前状态、下一步可能结果、后续动作与净材料消耗纳入动态规划或等价最优停止模型，比较“继续”和“弃置换胚子”。新胚子的期望价值应与同一策略一致计算，不能简单用下一条期望加分决定是否继续。

当前通过 Dinkelbach 分式优化最小化单胚 $C/p$：以全开策略为可行初值，向后求继续/回收动作，重新计算同一政策的成功率、经验和打孔器，再更新新胚子累计成本直到收敛。达标后强制支付尾费；胚子成本为零时排除未观察直接弃置的免费空转；成本全零按更高成功率平分。界面展示当前件费用和包含后续重开的累计费用，二者明确分开；策略报错不影响评分。

已消耗且不可回收的资源属于沉没成本，不应单独成为继续理由；可回收资源必须计入弃置与后续动作的成本。

特殊状态：

- 已达目标但未开满：必须保留并继续升至 +25、开满剩余词条，不得提前结束。
- 已达目标且五条开满：培养完成，后续普通开孔成本为零。
- 理论最高分也无法达标：建议弃置或调整目标。
- 已激活 5 条仍未达标：普通调谐流程结束；重构作为后续独立策略功能。
- 目标不可能实现：显示“不可达”，不能展示有限的期望成功成本。
- 成本数据或收益模型缺失：显示缺失项；仍可展示评分及概率，不给出伪精确的最优建议。

建议必须附简短依据，例如剩余达标概率、继续与重开的成本比较，以及结果依赖的假设。

## 6. OCR 扩展设计

OCR 不直接修改计算核心，而是将截图转换为待确认的标准输入。

流程：**手动截图或区域截取 → 图像预处理 → OCR 引擎 → 词条解析 → 数据校验 → 用户确认 → 更新声骸状态**。

### 接口约定

- 输入：图像及可选识别区域。
- 输出：词条标识、数值、原始文本、位置、置信信息和解析警告。
- 词条标识与现有 JSON 保持一致；百分比以百分点存储。
- OCR 引擎与词条解析器分离，支持替换引擎、维护中文别名和纠错规则。
- 将低置信、重复类型、非法档位、超过 5 条及未知文本标为待确认，不静默填入或强行修正。
- 在无法可靠判断主词条和副词条区域时要求用户确认，防止混入主词条。

第一版仅预留接口和入口，手动录入与 OCR 共用同一校验流程。后续可对比本地 OCR 引擎，按中文识别效果、Windows 部署、模型体积和许可选择。

默认本地识别，不上传截图。不读取游戏进程内存、不注入游戏、不自动点击调谐；OCR 的范围是识别屏幕信息与辅助录入。

## 7. 模块边界

| 模块       | 职责                                                     |
| ---------- | -------------------------------------------------------- |
| 数据配置   | 加载属性概率、预设、角色参数与成本，执行版本与合法性校验 |
| 领域模型   | 表示声骸、已激活词条、评分目标与材料成本                 |
| 权重引擎   | 计算系统权重、应用预设和用户覆盖                         |
| 评分引擎   | 计算当前分数、贡献明细与可达上界                         |
| 概率引擎   | 构造后续词条及分数的条件分布                             |
| 策略引擎   | 计算达标成本并比较继续、停止和换胚子                     |
| 桌面界面   | 编辑状态、调度后台任务、展示解释                         |
| OCR 适配层 | 图像识别与标准输入转换，可选加载                         |

计算核心不依赖 PySide6 或 OCR，便于独立测试和未来替换界面。缓存键应覆盖概率版本、权重、目标、成本、已激活类型与数值，以及必要的收益模型输入。

## 8. 实施顺序与验收

1. **计算原型**：验证配置，实现手动权重、当前评分和下一条条件分布。
2. **策略算法**：补齐成本数据，计算目标概率、净成本和继续建议；用小状态枚举与独立模拟交叉验证。
3. **Windows 桌面版**：实现录入、预设、目标设置、后台估算与配置保存。
4. **系统辅助权重**：先支持有明确收益模型的角色，展示计算依据与输入缺失状态。
5. **Windows 发布**：在未安装 Python 的 Windows 环境验证启动、配置写入和中文显示。
6. **OCR 扩展**：接入截图识别、确认编辑与识别回归样例，不改变已有核心接口。

重点测试：概率归一化、类型不重复、官方档位匹配、分数上界、不可达目标、满槽状态、权重覆盖、材料回收、异步结果过期以及 OCR 错误输入。

## 9. 当前结论

采用 **Python + PySide6** 实现 Windows 桌面 EXE；先建立独立且可验证的计算核心，再实现界面。权重使用“系统计算 + 角色预设 + 用户覆盖”的混合机制。OCR 作为可替换的本地输入扩展保留，不与评分和策略计算耦合。
